## 1. 产品定义

本产品是嵌入人工客服工作台右侧的 **客服辅助 Copilot**。它按当前消息时间点还原服务轨迹，精确关联聊天、订单、物流和售后工单，识别用户意图、可观察的情绪信号和服务风险，给出带证据的可编辑回复与下一步处理建议；发送、升级和资金相关动作始终由人工确认。

核心价值表述：

> 帮助客服更快定位事实、更稳判断风险、更有边界地处理下一步。

本产品不是面向消费者的自动客服，也不声称已经证明消费者满意度或情绪改善。

## 3. 用户和使用场景

### 3.1 目标用户

- **人工客服**：在接待过程中快速了解用户历史、当前订单和已发生的服务动作，减少重复询问。
- **客服主管**：查看风险队列和处置状态，定位未闭环事件。

### 3.2 三栏工作台

1. **左栏：会话/风险队列**
   - 会话 ID、买家昵称、场景、风险等级、处置状态。
   - 按风险等级、场景和状态筛选。
   - 高风险由规则触发；模型不能自行降低等级。
2. **中栏：聊天区**
   - 买家/客服消息按时间排列。
   - 可逐条推进到某条消息，模拟当时客服可见的信息。
   - 图片消息显示内容类型、路径和分析状态。
3. **右栏：Copilot 区**
   - 当前 `as_of_time`。
   - 服务轨迹摘要。
   - 意图、事实、缺失字段、情绪信号、风险等级。
   - 证据卡：原句、订单字段、工单字段、政策条款及时间。
   - 可编辑回复草稿。
   - 工单草稿与人工确认动作。
4. **顶部状态条**
   - 当前案例、Provider、在线/Mock 状态、Token、响应时间、工具调用数。

## 4. 核心流程

```text
打开会话
→ 选择当前消息时点
→ 获取截止该时点的聊天
→ 精确关联可见订单、物流和工单
→ 生成服务时间线
→ 运行规则风险检查
→ 按需检索政策/话术
→ Agent 生成结构化分析和回复草稿
→ 校验证据、风险等级和安全边界
→ 人工编辑并确认回复/工单草稿
→ 风险状态进入跟踪队列
```

## 5. 核心案例

### S00015：不良反应、就医、投诉升级

用途：展示高风险识别、时间快照、补问字段、安全边界和人工升级。

事实约束：首条消息为 `16:33:33`，不良反应工单 `BLFY61738711` 实际创建于 `17:13:33`，完成于 `23:56:33`。首条消息时不能显示工单或最终状态；只有达到相应时间点后才可见。

### S00024：空包裹、异常仅退款、待核实

用途：展示自述与证据的区分、待核实建议和防止未来工单泄漏。

首条消息只有用户自述，没有照片、称重和出库证据。工单 `KOC3195289` 实际创建于 `22:15:52`。正确输出为异常仅退款风险候选/待核实，建议保留外箱和面单、补六面照片、查询出库和揽收重量；不能断言欺诈或空包裹已证实。

### S00001：泵头破损、换货

用途：展示普通售后意图识别、图片消息关联和换货回复草稿。

官方 Excel 含 `image_path` 字段和 29 条图片消息，但目录没有真实图片文件，Excel 也没有嵌入图片。视觉分析只作为扩展，不能成为核心评分依赖。若后续使用 Image 2.5 生成图片，必须标记为合成数据。

## 6. 数据规格

### 6.1 已核对源数据

- 聊天记录：998 行、138 个会话、112 个买家。
- 订单：113 条。
- 工单：补发换货 24 条、线下打款 13 条、物流 15 条、不良反应 10 条、售后退货 18 条，共 80 条。
- 全部为虚构 MOCK 数据。

### 6.2 关联规则

- 主键：`session_id`（会话 ID）。
- 订单关联：`order_id`，必要时使用买家昵称和会话 ID交叉校验。
- 工单关联：`workorder_id`，但必须同时满足创建时间条件。
- 事实查询使用精确关联；向量检索只用于政策、产品说明和话术规范。

### 6.3 时间快照唯一真相

每次分析必须携带 `as_of_time`，并按字段分别过滤：

```text
chat.message_time <= as_of_time
order.下单时间 <= as_of_time；付款时间、发货时间、订单状态分别断言 <= as_of_time
workorder.create_time <= as_of_time
workorder.complete_time != null 且 workorder.complete_time <= as_of_time 才显示完结状态与完成时间
```

工单创建前返回 `no_workorder`；完成前不能展示“已完结”和完成时间。聊天表事后回填的“关联订单号/关联工单号”仅作潜在关联键，不能绕过以上过滤。订单号、工单号等 ID 必须按字符串读取。

已登记的源内冲突：S00015 消息 4（16:38:49，客服）称“已为您建立不良反应专项工单”，但工单 `BLFY61738711` 创建于 17:13:33。该时间区间内必须同时展示聊天原句与“工单系统暂无记录”，标记 `source_inconsistency`。

如果源数据冲突，返回 `source_inconsistency`，保留各来源，不由模型自行挑选一条。

## 7. Agent 和工具规格

### 7.1 编排选择

采用 **一个主 Agent + 结构化工具**。不采用互相传话的多 Agent team。程序负责数据权限、时间过滤、规则风险和动作确认；模型负责抽取、归纳、解释和生成草稿。

### 7.2 工具

```text
get_conversation_until(session_id, as_of_time)
get_order_snapshot(session_id, order_id, as_of_time)
get_workorder_snapshot(session_id, order_id, as_of_time)
get_service_timeline(session_id, as_of_time)
check_risk_rules(snapshot)
retrieve_policy(query, as_of_time)
draft_reply(snapshot, policy, risk)
create_workorder_draft(snapshot, action)
```

所有工具只读或生成草稿，不直接执行发送、退款、赔偿、打款或外部升级。

### 7.3 推荐调用顺序

1. 由消息序号得到 `as_of_time`。
2. 查询截止当前时间的聊天。
3. 精确查询当前可见订单和工单。
4. 生成服务时间线。
5. 运行规则风险检查。
6. 必要时检索政策。
7. Provider 生成结构化分析和回复草稿。
8. 通过事实引用、风险降级和安全边界校验。
9. 返回 UI 并记录调用日志。

## 8. 输出契约

Provider 必须返回可校验 JSON，最小字段如下：

```json
{
  "session_id": "S00024",
  "message_no": 1,
  "as_of_time": "2026-05-05T21:38:52",
  "intent": {
    "major": "售后服务",
    "minor": "异常仅退款",
    "confidence": 0.86
  },
  "emotion": {
    "negative_signal": "present",
    "escalation": "unclear",
    "evidence_refs": ["chat:S00024:1"]
  },
  "risk": {
    "type": "abnormal_refund",
    "level": "P1",
    "status": "needs_verification",
    "rule_ids": ["R-REFUND-001"]
  },
  "facts": [],
  "missing_fields": ["外箱照片", "面单照片", "出库/揽收重量"],
  "reply_draft": "……",
  "recommended_actions": ["收集证据", "创建工单草稿"],
  "needs_human_confirmation": true,
  "source_refs": ["chat:S00024:1", "policy:POL-REFUND-001"]
}
```

### Provider

- `QwenProvider`：云端 Qwen 系列主模型。
- `MockProvider`：固定案例和结构化输入，离线稳定复现。
- `RuleProvider`：模型不可用时输出最小结构化结果。

三者必须共用同一 JSON 契约。Qwen 失败时自动降级，不阻塞现场演示。

## 9. 情绪、意图和风险

### 9.1 情绪

赛题要求考察情绪判断和情绪升级，但没有规定一套心理学分类。本产品只标注当前文本和服务进展中的**可观察服务情绪信号**，不做心理诊断：

```text
negative_signal: none | present | unclear
escalation: no | yes | unclear
```

证据只能来自当前时点及此前的买家原话和服务进展。历史投诉可以在后续缓和后降级，但不能被删除。

### 9.2 风险等级与类型

| 等级 | 定义 | 示例触发 |
|---|---|---|
| P0 | 人身安全、就医或监管升级，须即时人工介入 | 不良反应+就医证据；监管投诉且情绪升级 |
| P1 | 资金或风控相关，须当日核实处理 | 异常仅退款候选；重复退款模式 |
| P2 | 体验类负面情绪，标准流程内处理 | 保价争议负面语气 |
| 待定级 | 证据不足 | `needs_verification`，禁止模型直接给 P0/P1 |


```text
adverse_reaction
complaint_escalation
abnormal_refund
repeat_contact
logistics_exception
unresolved_workorder
none
unclear
```

风险等级由规则定级，模型解释并指出证据/缺失字段；模型不能降低规则确定的高风险。

### 9.3 已核对反例

- S00064、S00065：曾威胁投诉，后续明确“不投诉了”，当前应“已缓和/继续跟踪”。
- S00087：从投诉威胁到“处理效率还行”，用于验证升级随服务进展下降。
- S00003、S00042、S00060：保价争议中的负面语气，应是普通负面信号和 P2。
- S00010、S00070、S00082：不良反应信息不完整或仍在观察，应停用/补问/回访，不做医学诊断。
- S00134、S00303、S00474：出现“医生/产检医生”语义，但不是就医事件，不应关键词触发 P0。
- 严格按“医院”字面检索，当前数据中只有 S00015、S00154、S00268，均属真实就医链路；不得编造不存在的非升级反例。

## 10. 规则、政策和动作边界

### 10.1 规则优先

规则包负责风险、必问字段和禁止动作。每条规则带 `rule_id`、来源、版本和生效时间。

### 10.2 政策包

先维护 10–20 条轻量政策/话术规则，覆盖收证、升级、退款边界和回复规范。团队补充内容标为“比赛演示规则”，不能伪装成官方政策。

### 10.3 人工确认

以下动作都必须人工点击确认：发送回复、升级、创建/更新工单、退款、赔偿、线下打款。Demo 只生成草稿或模拟动作，不连接真实业务系统。

## 11. 评测规格

### 11.1 开发集/冻结测试集

本项目不训练 Qwen 基础模型，因此使用“开发集”和“冻结测试集”，不把它们称作训练集：

- 48 个会话：开发集，用于提示词、规则、字段映射和 UI 调整。
- 12 个会话：冻结测试集，用于最终报告，冻结后不再调参。
- 同一买家的所有会话放在同一集合；同一服务事件的所有消息时点放在同一集合。
- 评测单位是 `(session_id, message_no, as_of_time)`，不是整段会话最终结果。

### 11.2 四组对照

1. `Chat-only`：只有当前及历史聊天文本。
2. `Snapshot`：聊天、当前可见订单/工单和统一版本政策，一次模型调用。
3. `Full Agent`：工具查询、时间快照、规则前置、结构化输出和动作边界。
4. `Rules-only`：零模型调用，仅运行规则和数据过滤，用于区分规则贡献与模型增量。

四组保持相同政策版本和测试时点；模型组保持相同模型与参数，只改变信息可见范围与编排。风险指标以 Rules-only 为参照。

### 11.3 指标

- 意图：Macro-F1、各类召回率。
- 情绪：严格准确率、安全覆盖率。
- 风险：P0/P1 召回率、漏报率、误报率。
- 事实：字段准确率、服务轨迹关联准确率、引用完整率。
- 回复：情绪回应、事实准确、下一步可执行、边界安全四项人工评分。
- 工程：Token、调用次数、响应时间、Mock 连续运行成功率。
- 安全：错误类型计数。
- `unclear`：覆盖率为预测非 `unclear` 的样本占比；严格准确率仅在覆盖样本上计算；gold 为 `unclear` 时仅预测 `unclear` 记为正确。安全覆盖率为未发生高风险漏报、`unsafe_reply`、`future_information_leak` 的样本占比。

固定错误类型：

```text
missing_fact
wrong_join
wrong_intent
wrong_emotion_signal
wrong_risk_level
unsupported_claim
unsafe_reply
unnecessary_escalation
future_information_leak
```

规则输出不能直接充当标准答案；两人独立标注后讨论冲突，`unclear` 是合法标签。

## 12. 成本和性能要求

- 规则和结构化查询先于模型调用。
- 对聊天历史按时间窗口压缩，保留关键原句。
- 订单和工单使用精确关联；向量检索只用于政策、产品和话术。
- 对同一 `session_id + message_no + provider_version` 缓存分析。
- 记录输入/输出 Token、调用次数、响应时间和降级原因。
- Demo 的降级路径必须完整走通，不能只显示错误提示。

## 13. 早鸟验收标准

核心主线达到以下条件即可作为早鸟候选版本：

- S00015、S00024、S00001 三个案例稳定运行。
- Mock 无网络、无密钥可连续演示；Qwen 失败自动降级。
- 评测命令能一键输出四组对照、指标和错误类型。
- 所有时间泄漏测试通过。
- 高风险、发送和资金相关动作都需人工确认。
- 没有已知事实编造、医学诊断或无依据定责。
- 从打开会话可走到证据、回复草稿、工单草稿和风险跟踪。

扩展项（主线稳定后即可加入，提交日期以官方通知为准）：视觉模型、合成图片、更多案例、主管统计和更细的成本曲线。
