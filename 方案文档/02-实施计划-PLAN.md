## 总体依赖与并行

- A 的 loader/快照先于 B 的运行规则和 C；B 的契约先于 C；C 的统一 JSON 先于 D；候选版本和真实报告先于 F。
- EVAL-T001 的数据划分准备可以在 B–D 实现前进行；正式标签冻结必须遵循锁定的风险/情绪契约，最终四组运行依赖 AGENT-T004。
- 字段审计、政策内容草拟、静态 UI 回归可在满足各自前置后并行；冻结后不能用冻结结果调参。
- AGENT-T002 的三案例运行通过 AGENT-T001→RISK-T004→RISK-T001→DATA-T004 间接依赖主案例基线，无需重复添加同一前置。

## 交付目标与工程约定

目标交付为本地可运行 React + Vite / FastAPI Demo，目录建议为 backend、frontend、data、eval、docs，并提供 README、.env.example、requirements.txt。实际工程目录尚未交付，目标描述不能标为完成。

必须交付：三栏工作台、S00015/S00024/S00001、时间一致多源关联、Qwen/Mock/Rule 统一契约、规则/证据/人工确认/工单草稿、48/12 和四组评测、真实报告、Demo/PPT/README/离线说明。视觉、更多案例、主管统计、状态趋势和细化成本曲线均为主线稳定后的扩展。

## 两人协作与交接

两人按垂直切片轮换：S00015 高风险、S00024 待核实、S00001 普通售后/图片扩展、评测与展示。每人每日保留变更说明、可复现命令、已知问题和下一步接续点；先定 JSON 契约，再并行前后端；另一人必须用 Mock 路径复核已完成切片。

每个功能要有可操作入口和最小验证样本；未验证数字不得写入 PPT/视频。协作内容是执行约定，不改变产品规则。

## Git 与版本标签

目标标签为 baseline-data、core-flow-ready、eval-ready、submission-candidate。每个标签配 CHANGELOG 或发布说明，记录已完成能力、验证命令、已知限制和下一版风险。本次只记录约定，不创建标签、提交或发布。

## 总验收门槛

A–F 门槛必须由阶段文件链接的 C-ID 逐项通过：三主案例真实运行、Mock 离线连续可用、Qwen 失败降级、时间/来源冲突回归、证据与缺失字段、人工确认、无医学诊断/无依据定责、四组真实评测、PPT/视频数字可追溯。静态 UI 通过不能替代数据/Agent/Provider/评测门槛。

## 风险应对

| 风险 | 触发信号 | 处理 |
|---|---|---|
| Qwen 网络/密钥失败 | 超时、鉴权失败 | 自动 Mock/Rule，记录原因 |
| 工单时间泄漏 | 早期显示未来状态 | 统一快照仓库和回归 |
| 负面语气误报 | 反例被升高 | 规则定级，模型不能改等级 |
| 信息不足过度断言 | S00024 等输出已证实结论 | needs_verification、缺失字段和证据 |
| 图片素材缺失 | Excel 有路径无文件 | 主流程不依赖视觉，扩展标合成 |
| 冻结集污染 | 冻结结果反复变化 | 版本登记、hash、冻结后只运行 |
| 展示与技术脱节 | PPT 数字/界面不符 | 冻结报告后制作物料并复核 |
