# PLAN：数据共情者——消费者的 AI 管家

- **版本**：v0.1
- **日期**：2026-09-12
- **目标**：在早鸟截止时间（须以官方通知出处核实后登记）前，交付可离线演示、可量化评测、可录制视频和可写入 PPT 的核心版本
- **团队**：2 人；每人每天 3–5 小时
- **原则**：两人均参与前端、后端、模型、数据和展示；按垂直功能切片衔接，不按“一个只做技术、一个只做展示”分工

## 2. 实施顺序

### 阶段 A：基线与数据契约

目标：任何人都能在本机复现同一个数据快照。

任务：

- 建立工程目录和 Git 仓库。
- 复制/只读引用官方 Excel，写数据加载器和字段映射。
- 规范 `session_id`、`message_no`、`order_id`、`workorder_id`、`as_of_time`。
- 实现时间过滤：工单创建前不可见、完成前不可显示完结。
- 输出三份基线样本：S00015、S00024、S00001。
- 写最小数据自检：行数、表名、主键、时间单调性和空值。

完成标准：同一条消息在任意运行中得到相同快照；S00015 首条消息看不到未来工单。

### 阶段 B：规则、政策和结构化契约

目标：先把事实与安全边界固定，再接模型。

任务：

- 建立 `risk_rules`：不良反应、投诉升级、异常退款、重复进线、物流异常、未闭环工单。
- 固定风险类型和 `negative_signal` / `escalation` 标签。
- 建立 10–20 条轻量政策包，带 `rule_id`、来源、版本和生效时间。
- 定义 Provider JSON Schema 和校验器。
- 写动作边界：发送、升级、工单、退款、赔偿、打款均需人工确认。

完成标准：模型输出不能绕过时间过滤和规则风险；缺证据时能返回 `unclear` 或 `needs_verification`。

### 阶段 C：Agent 与三种 Provider

目标：在线 Qwen 可用，离线 Mock 永远可用。

任务：

- 实现一个主 Agent 编排器。
- 接入结构化工具：聊天、订单、工单、时间线、规则、政策、回复、工单草稿。
- 实现 `MockProvider`，固定主案例和反例的稳定输出。
- 实现 `RuleProvider`，在模型失败时输出最小可用 JSON。
- 实现 `QwenProvider`，从环境变量读取配置，失败时自动降级。
- 记录 Provider、模型、规则版本、政策版本、Token、耗时和调用数。

完成标准：断网/无密钥下三案例连续运行；在线时 Qwen 输出仍通过同一契约校验。

### 阶段 D：工作台 UI

目标：让评委一眼看懂客服实际如何使用。

任务：

- 左栏实现会话和风险筛选。
- 中栏实现逐条推进、买家/客服气泡、图片消息状态。
- 右栏实现服务轨迹、事实证据、意图/情绪/风险、回复草稿、工单草稿。
- 顶部显示当前时点、Provider、Mock/在线、Token、响应时间和调用数。
- “使用此回复”只写入编辑框；“创建工单”只生成草稿。
- 对高风险和资金动作显示人工确认状态。

完成标准：从打开会话可走到证据、回复草稿、工单草稿和风险跟踪；无按钮是静态摆设。

### 阶段 E：评测与冻结

目标：形成可写进 PPT 的可信结果。

任务：

- 整理 48 个开发会话和 12 个冻结测试会话。
- 同一买家、同一服务事件不跨集合。
- 建立两人独立人工标注流程，保留证据消息和来源。
- 运行 Chat-only、Snapshot、Full Agent、Rules-only 四组对照。
- 计算意图、情绪、风险、事实、回复、安全和成本指标。
- 加入投诉缓和、负面非高风险、待核实、医疗词边界和时间泄漏反例。
- 生成 JSON/CSV/Markdown 报告，记录版本。

完成标准：冻结后不因测试结果调参；报告能定位到样本、错误类型和证据。

### 阶段 F：展示物料和候选提交

目标：把真实系统能力压缩成清晰的评审材料。

任务：

- 用三个主案例录制三分钟视频。
- PPT 按“痛点—方案—Agent—证据—评测—价值—规划”组织。
- 准备离线启动说明、Qwen 配置说明和故障降级说明。
- 统一对外表述：改善事实定位、风险判断和处理建议，不夸大为满意度证明。
- 建立 `submission-candidate` 标签，打包源代码和运行指南。

完成标准：现场电脑无网/无密钥可以走通 Mock 主流程；视频和 PPT 中的数字来自冻结测试报告。

## 3. 两人协作方式

### 3.1 按垂直切片协作

每个切片由一人主做、另一人当天复核并补齐相邻层，下一切片轮换：

- **切片 1：S00015 高风险链路**：数据快照 + 规则 + Agent + UI + 评测一起完成。
- **切片 2：S00024 待核实链路**：同上，重点验证证据不足和未来工单过滤。
- **切片 3：S00001 普通售后/图片扩展**：同上，重点验证图片消息状态。
- **切片 4：评测和展示**：两人共同复核指标、脚本和 PPT，避免展示与技术脱节。

### 3.2 每日节奏

每人 3–5 小时可按以下比例调整：

- 20%：同步、读日志、确认接口契约。
- 60%：当天垂直切片实现。
- 20%：互相复核、运行自检、记录 Git。

每天结束至少留下：变更说明、可复现命令、已知问题和下一步接续点。

### 3.3 衔接规则

- 先定 JSON 契约，再并行写前端和后端。
- 每个功能必须有一个可操作入口和一个最小验证样本。
- 不在同一时间修改同一核心文件；跨层变更先写接口说明。
- 任一人完成的切片，另一人必须用 Mock 路径跑一遍。
- 不把尚未验证的数字写入 PPT 或视频字幕。

## 4. Git 和版本标签

不锁死具体中间日期，按完成度及时保存版本：

```text
baseline-data
core-flow-ready
eval-ready
submission-candidate
```

每个标签对应一份 `CHANGELOG.md` 或发布说明，记录：

- 已完成能力；
- 已验证命令和结果；
- 已知限制；
- 下一版风险。

## 5. 验收门槛

### 5.1 核心门槛

- 三个主案例稳定运行。
- Mock 无网络/无密钥连续运行不阻塞。
- Qwen 失败自动降级。
- 时间快照和未来工单泄漏测试通过。
- 事实、风险、回复均带证据或缺失字段。
- 高风险、发送、资金动作均需人工确认。
- 无医学诊断、无无依据定责、无事实编造。
- 评测可一键运行并输出真实结果。

### 5.2 质量门槛

- UI 从客服工作台角度可理解，不堆花哨功能。
- 右栏建议不会遮挡聊天主流程。
- 关键状态有明确文字，不能只靠颜色。
- 任何在线依赖都有离线替代路径。
- 现场演示时可解释“为什么这样判断”和“证据在哪里”。

## 6. 风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| Qwen 网络/密钥失败 | 调用超时、鉴权失败 | 自动切 Mock/Rule，顶部显示降级原因 |
| 工单时间泄漏 | 首条消息出现未来状态 | 所有查询集中走 `as_of_time` 仓库，加入回归测试 |
| 模型把负面语气判成高风险 | S00003/S00042/S00060 误报 | 风险规则结合业务场景，模型不得改等级 |
| 信息不足时过度断言 | S00024/S00010 输出已证实结论 | 强制 `needs_verification`、缺失字段和证据引用 |
| 图片素材缺失 | Excel 有路径但文件不存在 | 图片分析做扩展，主流程不依赖；合成图片明确标注 |
| 评测集被调参污染 | 冻结测试结果反复变化 | 测试集登记版本，冻结后只运行不修改 |
| 展示和技术脱节 | PPT 数字/界面与真实运行不一致 | 视频录制前用候选版本重新跑评测并截图 |

## 7. 评测、PPT、视频的接续关系

- 评测先产出真实数字，再写 PPT。
- PPT 中每个核心结论都能回到某个案例、指标或证据卡。
- 视频严格按三分钟脚本：S00015 → S00024 → S00001 → 评测摘要。
- 现场 Demo 默认 Mock；如果切换 Qwen，必须同时展示 Provider 和降级状态。
