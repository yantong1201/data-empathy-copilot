# 数据共情者——消费者的 AI 管家

## 方案冻结版（详细长文档）

- 文档状态：已确认，可作为产品、评测和展示共同基线
- 版本：v0.1
- 日期：2026-09-12
- 目标通道：优先早鸟通道；早鸟提交截止时间待以官方通知核实并登记

## 一、核心判断

本赛题的重点不是做一个面向消费者的自动聊天机器人，而是做一个真正嵌入人工客服工作台的辅助工具。评委需要看到客服在处理一条真实进线时，系统怎样把多源业务数据串起来、怎样给出有证据的情绪和风险判断、怎样生成可编辑回复，以及怎样把处置动作留给人工确认。

产品的一句话定义：

> 证据驱动的服务共情闭环：理解当前可观察的情绪信号，核对事实，判断风险，辅助人工完成处理。

固定主流程：

```text
打开会话
→ 按时间还原服务轨迹
→ 关联订单物流字段、物流工单和其他售后工单
→ 判断意图、可观察情绪信号和风险
→ 展示证据
→ 生成可编辑回复草稿
→ 人工确认
→ 创建/更新工单草稿
→ 跟踪风险状态
```

## 二、赛题要求逐项落地

### 1. 核心功能完整性与实用性

产品采用千牛三栏工作台形态：左侧会话/风险队列，中间聊天，右侧 Copilot。右栏不遮挡聊天主流程，所有建议都能回溯到证据。主流程覆盖打开会话、分析、回复和工单草稿，风险队列覆盖 open、watching、resolved 状态。

### 2. 大模型智能分析准确度

系统不只展示一句模型总结，而是展示：

- 当前意图及置信度；
- 当前可见订单、物流和工单事实；
- 情绪信号和证据原句；
- 风险类型、等级、规则 ID；
- 缺失字段和待核实事项；
- 回复草稿中的事实来源。

通过开发集、冻结测试集、四组对照和错误类型来量化效果。

### 3. 技术创新与场景价值

创新点不是堆叠多个 Agent，而是把时间快照、精确关联、规则风险和模型解释组合为客服实际可用的证据链。多模态保留为可插拔扩展，避免官方数据没有真实图片时为了“看起来有视觉”而虚构识别结果。

### 4. 模型性能与成本优化

规则和精确数据查询先于模型调用；历史聊天只保留当前相关窗口和关键原句；同一会话时点缓存分析；记录 Token、调用次数、响应时间和降级原因，形成效果—成本对比。

## 三、用户和界面

### 客服使用路径

1. 选择一个进线会话。
2. 系统定位当前消息时间点。
3. 右栏展示截止当前时点的服务轨迹。
4. 客服查看订单、物流和工单事实。
5. 系统给出意图、情绪、风险和待补信息。
6. 客服编辑并确认回复草稿。
7. 如有必要，生成工单草稿并确认跟踪。

### 三栏布局

**左栏**用于扫描：会话 ID、买家昵称、场景、风险等级、处理状态和筛选条件。

**中栏**用于阅读：买家/客服气泡按时间排列，消息序号和内容类型可见，支持逐条推进。

**右栏**用于决策：时间线摘要、事实、证据、意图、情绪、风险、回复和动作按顺序排列。

顶部必须显示当前案例、Provider、Mock/在线状态、Token、响应时间和工具调用数，让评委能同时看懂产品和工程状态。

## 四、三个主案例

### S00015：不良反应、就医、投诉升级

它代表高风险场景。演示时先停在首条买家消息，再逐条推进，先展示消息时点的 `no_workorder`，再切换到工单创建后和完成后时间档；风险变化必须绑定证据和规则。

事实：首条消息 `16:33:33`；工单 `BLFY61738711` 实际创建 `17:13:33`，完成 `23:56:33`。首条消息时不得显示工单、完成状态和“是否就医=是”。

系统应该先识别症状和关切，要求补充年龄、肤质、出现时间、停用和就医等字段；当达到就医等高风险证据后，由规则提升风险并给出人工升级建议。回复不能做医学诊断或承诺因果。

### S00024：空包裹、异常仅退款、待核实

它代表证据不足和风控平衡。首条消息只有用户自述，没有照片、称重和出库证据，工单 `KOC3195289` 实际 `22:15:52` 才创建。

正确结果：异常仅退款风险候选、状态待核实；建议保留外箱和面单、补六面照片、查询出库和揽收重量。不能断言空包裹已证实，更不能直接认定欺诈或自动退款。

### S00001：泵头破损、换货

它代表普通售后场景。系统需要识别破损换货意图，关联订单和图片消息，生成收证、换货或补发回复草稿。

当前 Excel 有 `image_path` 字段和 29 条图片消息，但目录没有真实图片文件，Excel 也没有嵌入图片。因此视觉分析不作为核心评分依赖。后续可以使用 Image 2.5 生成合成图片作为扩展，并在界面和文档中明确标记“合成数据”。

## 五、数据事实和时间一致性

### 已核对事实

- 聊天记录 998 行、138 个会话、112 个买家。
- 订单 113 条。
- 工单共 80 条：补发换货 24、线下打款 13、物流 15、不良反应 10、售后退货 18。
- 全部是虚构 MOCK 数据。
- 聊天表的关联工单号存在事后回填。

### `as_of_time` 规则

每次分析都必须绑定一个 `as_of_time`，所有查询集中通过数据仓库完成：

```text
chat.message_time <= as_of_time
order.event_time <= as_of_time
workorder.create_time <= as_of_time
workorder.complete_time <= as_of_time 才能显示完结状态和完成时间
```

工单创建前返回 `no_workorder`；完成前不能显示“已完结”和完成时间。若聊天表填了未来工单号，也只能作为潜在关联键，不能绕过时间过滤。

源数据冲突时返回 `source_inconsistency`，保留冲突来源，不能让模型自行挑选一条。

## 六、Agent 设计

### 编排

采用一个主 Agent 加结构化工具，不采用互相传话的多 Agent team。程序掌握数据可见性、规则风险和动作边界；模型掌握抽取、归纳、解释和草稿生成。

### 工具

```text
get_conversation_until
get_order_snapshot
get_workorder_snapshot
get_service_timeline
check_risk_rules
retrieve_policy
draft_reply
create_workorder_draft
```

工具返回结构化 JSON 和 `source_refs`。任何工具都不执行真实发送、退款、赔偿、打款或外部升级。

### 推荐顺序

1. 由消息序号得到 `as_of_time`。
2. 查询截止时点的聊天。
3. 精确查询可见订单和工单。
4. 生成服务时间线。
5. 运行风险规则。
6. 按需检索政策。
7. 调用 Provider 生成结构化分析和回复草稿。
8. 校验事实引用、风险等级和安全边界。
9. 返回 UI，记录日志和成本。

### Provider

- `QwenProvider`：云端 Qwen 系列主模型。
- `MockProvider`：无网络、无密钥时稳定复现案例。
- `RuleProvider`：模型不可用时输出最小可用结构。

Provider 切换不能改变 UI 和评测接口；Qwen 失败必须自动降级并显示原因。

## 七、情绪、意图和风险口径

### 情绪不是心理诊断

赛题要求考察情绪判断和情绪升级，但没有规定心理学分类。本方案标注的是客服能从当前文本和服务进展观察到的信号：

```text
negative_signal: none | present | unclear
escalation: no | yes | unclear
```

“医生”“产检医生”等词本身不等于就医高风险；需要结合症状、是否就医和业务上下文。历史投诉在后续缓和后可以降级，但保留历史事件。

### 风险类型

```text
adverse_reaction
complaint_escalation
abnormal_refund
repeat_contact
logistics_exception
unresolved_workorder
none
unclear
```

风险级别由规则确定；模型负责解释、引用证据和指出缺失字段，不能自行降低规则确定的高风险。

### 反例边界

- S00064、S00065：先威胁投诉，后明确“不投诉了”，当前应“已缓和/继续跟踪”。
- S00087：从投诉威胁到“处理效率还行”，验证升级随服务进展下降。
- S00003、S00042、S00060：保价规则争议，语气负面但应是普通 P2。
- S00010、S00070、S00082：不良反应信息不完整或仍在观察，先停用、补问、回访。
- S00134、S00303、S00474：医生语义属于成分咨询，不应关键词触发 P0。
- 严格“医院”字面检索只有 S00015、S00154、S00268，均为真实就医链路；不编造不存在的非升级反例。

## 八、评测口径

### 数据集

由于不训练 Qwen 基础模型，使用“开发集”和“冻结测试集”而不是“训练集”：

- 48 个会话用于开发和调参。
- 12 个会话冻结后用于最终报告。
- 同一买家和同一服务事件不能跨集合。
- 评测单位是 `(session_id, message_no, as_of_time)`。

### 对照组

1. `Chat-only`：聊天文本。
2. `Snapshot`：聊天、当前可见订单/工单和统一版本政策，一次模型调用。
3. `Full Agent`：时间快照工具、规则前置、政策检索、结构化输出和动作边界。

四组保持相同政策版本和测试时点；模型组统一模型与参数，风险指标以 Rules-only 为参照。

### 指标

- 轨迹：事件关联准确率。
- 意图：Macro-F1 和各类召回率。
- 情绪：严格准确率和安全覆盖率。
- 风险：P0/P1 召回、漏报率和误报率。
- 事实：字段准确率和引用完整率。
- 回复：情绪回应、事实准确、下一步可执行、边界安全四项人工评分。
- 工程：Token、调用次数、响应时间、Mock 连续成功率。

固定错误类型：

```text
missing_fact
wrong_join
wrong_intent
wrong_emotion_signal
wrong_risk_level
unsupported_claim
unsafe_reply
unnecessary_escalation
future_information_leak
```

## 九、安全和动作边界

发送回复、升级、创建/更新工单、退款、赔偿、线下打款都必须人工确认。Demo 只生成草稿或模拟动作，不连接真实业务系统。

回复生成必须通过以下校验：

- 每个事实有来源；
- 缺证据时使用“待核实”而不是断言；
- 不做医学诊断；
- 不承诺赔付、退款时效或结果，除非当前可见政策和工单支持；
- 不把规则高风险降级；
- 不自动执行不可逆动作。

## 十、成本优化

- 规则和结构化查询先于模型调用。
- 历史聊天按时间窗口压缩，保留关键原句。
- 固定系统提示和政策前缀，尽量命中缓存。
- 订单、物流、工单使用精确关联；向量检索只用于政策、产品说明和话术。
- 缓存 `session_id + message_no + provider_version` 的分析结果。
- 每次运行记录 Token、调用数、耗时和降级原因。

## 十一、早鸟核心门槛

早鸟提交截止时间待以官方通知核实并登记，核实前不在方案中写死日期。

- 三个主案例稳定运行。
- Mock 无网无密钥连续演示；Qwen 失败自动降级。
- 评测一键运行并输出四组对照、指标和错误类型。
- 时间泄漏测试通过。
- 高风险、发送、资金动作都需人工确认。
- 无已知事实编造、医学诊断和无依据定责。
- 从打开会话走到证据、回复草稿、工单草稿和风险跟踪。

视觉扩展、更多案例和主管统计只能在主线稳定后加入；提交日期以官方通知为准，达到候选门槛即可保存版本，达到候选门槛即可及时保存版本。

## 十二、价值表述

统一使用：

> 通过时间一致的多源数据融合和证据驱动的 Agent 编排，帮助人工客服更快定位事实、更稳判断风险、更有边界地生成下一步处理建议。

不把 Demo 结果写成已证明消费者满意度提升、情绪改善或线上损失下降；这些属于后续上线后的待验证指标。
