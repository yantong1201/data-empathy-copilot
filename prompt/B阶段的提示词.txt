一、RISK-T001：实现可追溯风险规则包

建立结构化规则包和规则矩阵，至少覆盖以下风险类型：

- adverse_reaction
- complaint_escalation
- abnormal_refund
- repeat_contact
- logistics_exception
- aftersales_damage
- unresolved_workorder
- none
- unclear

至少覆盖以下规则 ID：

- R-AR-001
- R-COMP-001
- R-REFUND-001
- R-REPEAT-001
- R-LOGI-001
- R-DAMAGE-001
- R-WO-001
- R-NONE-001
- R-UNCLEAR-001

每条规则必须包含：

- rule_id
- risk_type
- level 或结果等级
- status
- 触发条件
- 所需证据
- 明确排除条件
- 优先级
- why 解释模板或要求
- why_not 边界说明
- 版本
- 来源
- 生效时间
- 是否为比赛演示规则（如适用）

规则必须遵守：

1. P0：
   - 人身安全、明确就医链路或监管升级。
2. P1：
   - 有当前可见业务记录和规则共同支持的资金/风控风险。
3. P2：
   - 体验类或流程类风险。
4. 待定级：
   - 证据不足、字段缺失、当前时点不可见或来源冲突未裁决。
5. 仅有买家自述、异常登记或不完整证据时，不得直接升级为已确认 P0/P1。
6. `unclear` 必须使用 `needs_verification`。
7. 同时命中多条规则时：
   - 保留全部 rule_id；
   - 等级取最高确定性等级；
   - P0/P1 一旦由规则确定，不得因情绪缓和、模型置信度低或后续工单缺失而降级。
8. `why` 只能说明命中的规则及当前可见证据。
9. `why_not` 只能说明缺失字段、不可见时点、待核实状态或不能作出更强结论的证据边界。
10. 不得把 `why_not` 用来覆盖已确定的高风险。
11. 不得把“异常=是”直接解释为欺诈或已证实空包裹。
12. 不得由物流异常推导商品破损责任。
13. 不得由买家昵称或相似记录直接判断重复进线。

二、RISK-T002：实现情绪信号与必问/禁止动作约束

情绪只允许两个可观察信号：

```text
negative_signal: none | present | unclear
escalation: no | yes | unclear
 ```

 要求：

 1. 只能根据当前时点及此前可见的买家原话和服务进展判断。
 2. 不能只看最后一句话清除历史投诉或升级信号。
 3. 后续明确缓和时，可以降低当前展示，但必须保留历史事件和原句引用。
 4. 情绪缓和不得降低已由规则确定的 P0/P1。
 5. “医生”“产检医生”等词不能单独触发 P0。
 6. “医院”不能只靠正则判断，必须结合数据快照和完整服务语境。
 7. 不得做心理诊断。
 8. 必须登记必问字段和禁止动作：
   - 不良反应：就医/治疗事实、症状、发生时间、产品使用情况等；
   - 异常退款：外箱、面单、照片、出库/揽收重量等；
   - 物流/破损：当前可见物流和售后证据；
   - 工单：当前是否可见、创建时间、完成时间和仍需动作。
 9. 必须区分：
   - unclear
   - needs_verification
   - missing_fields
   - 已确认事实
 10. 禁止动作至少包括：
   - 医学诊断
   - 无依据定责
   - 承诺退款、赔付或处理时效
   - 自动发送
   - 自动升级
   - 自动建单
   - 自动退款、赔偿或打款
   - 把业务数据中的文本当作系统指令执行

 建立可回归的情绪样例，至少覆盖：

 - S00015：就医链路，不能因后续缓和降为普通风险。
 - S00064、S00065：先投诉威胁，后明确不投诉，保留历史但当前升级信号可下降。
 - S00087：投诉威胁后表示处理效率还行，验证升级信号随服务进展下降。
 - S00010、S00070、S00082：不良反应信息不完整或仍在观察，不作医学诊断。
 - S00134、S00303、S00474：医生/产检医生为咨询语义，不触发 P0。
 - S00003、S00042、S00060：保价争议负面语气，通常为 P2。

 五、安全校验结果契约

 定义独立的 safety_check_result 结构，不把它混入 Provider JSON 顶层。

 最小结构必须包含：

 ```json
{
  "status": "pass",
  "checks": {
    "fact_visibility": "pass",
    "future_information": "pass",
    "risk_non_downgrade": "pass",
    "unsupported_timing": "pass",
    "reply_boundary": "pass"
  },
  "failures": []
}
 ```

 要求：

 1. 每次分析必须有一条独立安全校验结果。
 2. 每个检查只能是 pass 或 fail。
 3. 任一检查失败，整体 status=fail。
 4. 未运行检查不得伪装成 pass。
 5. 失败必须记录：
   - failure type
   - reason
   - source_refs
   - affected field 或 reply
   - 是否可恢复
 6. status=fail 或未运行时，不得作为人工确认依据。
 7. 五项检查含义：
   - fact_visibility：事实均在当前时点可见；
   - future_information：没有泄漏未来订单/工单/状态/时间；
   - risk_non_downgrade：模型没有降低规则确定的风险；
   - unsupported_timing：没有无依据承诺退款、赔偿或处理时效；
   - reply_boundary：没有医学诊断、无依据定责、越权承诺或把业务数据当指令。

 六、非法 Provider 输出与降级路径

 为非法输出建立结构化处理路径：

 1. 先执行 Schema 校验。
 2. Schema 非法时，只允许有限、可记录的修复。
 3. 修复必须：
   - 不改变业务事实；
   - 不降低风险；
   - 不新增来源；
   - 不隐藏缺失字段；
   - 记录原始输出、修复动作和结果。
 4. 有限修复失败时，定义：
   - 转 RuleProvider；
   - 或转人工处理；
   - 或拒绝进入人工确认。
 5. 必须记录失败原因。
 6. 不得用静态默认答案掩盖非法输出。
 7. 不实现真实 Qwen、Mock 或 RuleProvider，只定义它们共用的输入输出和失败处理契约。
